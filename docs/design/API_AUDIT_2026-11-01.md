## 2. Vertex Gemini (generation)

### 2a. Model options (measured)

| | `gemini-3.1-pro-preview` | `gemini-4-argon` |
|---|---|---|
| Stage | Public **preview** (Feb 19, 2026) | Generally available (Oct 13, 2026) |
| Region | `global` only | `global` only |
| Short answer latency | ~9 s | ~3 s |
| Thinking tokens on a 1-sentence answer | 565 of 607 output tokens | not reported |
| Lesson-sized JSON, effort default / medium / low | 42 s / 35 s / 25 s | 34 s / 25 s / 19 s |
| Lesson cost (LiteLLM estimate), default / medium / low | $0.046 / $0.040 / $0.025 | $0.022 / $0.015 / $0.014 |
| Structured output (JSON schema) | Valid, 10 terms, 4 components | Valid, 10 terms, 5 components |
| Tool call with thought signature | Works | Works |

**Estimated daily cost** (1 lesson + 2 tool loops of ~7 calls with growing context, medium effort): about **$0.30-0.45/day** for 3.1 Pro, **$0.20-0.30/day** for Argon, i.e. roughly $6-14/month. Estimate only; real figures come from the token log after the first runs.

### 2b. Input

| Parameter | Rule (Gemini 3/4) | Our code today | Fix |
|---|---|---|---|
| `vertex_location` | Must be `global` | Not set, defaults to `us-central1` -> 404 | Set from `.env` (`VERTEX_LOCATION=global`) |
| Thinking | `reasoning_effort` low / medium / high (maps to `thinking_level`); never combine with `thinking_budget` | Not set (HIGH default) | `medium` for lesson and agents (config) |
| Temperature | Keep default 1.0 (lower may loop) | Not set | Keep unset; add a test that forbids it |
| Structured output | `response_format` = `json_schema` | `json_object` (loose) | Use the lesson/JIT/JIC schemas |
| Tool-call history | Send the model's full message back (keeps thought signature) | `core/tool_agent.py` rebuilds it and drops the signature | Pass `message.model_dump()` |
| Timeout | Lesson takes 19-42 s | 30 s (`LITELLM_TIMEOUT_SECONDS`) | 180 s |

**Thought-signature test:** dropping the signature did not error (LiteLLM injects a placeholder), but reasoning tokens doubled (78 -> 159) on 3.1 Pro and one Argon call took 163 s instead of 9.5 s. Fix is required.

### 2c. Output

| Field | Meaning | Handling needed |
|---|---|---|
| `choices[0].message.content` | Text or JSON | Parse against schema |
| `finish_reason` = `stop` | Normal | OK |
| `finish_reason` = `length` | **Truncated, no exception raised** (probe: 9 characters returned) | Treat as failure: retry once with more output room / lower effort |
| `finish_reason` = `content_filter` / safety | Blocked, no exception | Log, retry once, else section fallback |
| `MALFORMED_FUNCTION_CALL` or empty content | Silent failure | Existing guard (CL-050) kept |
| `usage` (prompt, completion, reasoning tokens) | Billing basis; thinking billed as output | Log per call; budget guard |

### 2d. Errors: how Vertex reports them and what we do

| Error | Reported as (probe) | Retry? (Google guidance) | Our handling today | New handling |
|---|---|---|---|---|
| 400 invalid argument | `BadRequestError` / `UnsupportedParamsError` (raised before call) | No | Fails over to next model | **Fail fast**, CRITICAL log, alert |
| 401 / 403 auth | `AuthenticationError` | No | Fails over | Fail fast, alert "credentials" |
| 404 model or region | `NotFoundError`, JSON message names the model and region | No | Fails over | Fail fast, alert "model/region" |
| 429 quota / overload | `RateLimitError` | Yes, max 2, backoff from 1 s | Retries OpenRouter only | Retry same model 2x (honour Retry-After), then fallback |
| 500 / 503 | `InternalServerError` / `ServiceUnavailableError` | Yes, max 2 | Fails over | Retry same model 2x, then fallback |
| 504 / client timeout | `Timeout` (status 408 in LiteLLM) | Yes | Fails over | Retry once with same timeout |
| Network down (DNS) | `APIConnectionError` | Yes | Fails over (all models fail together, as on Jul 7 and 13) | Wait for network up to 5 min, then retry; if still down, log "offline" |

**Single-model gap:** with "Pro only" there is no next model, so today every error ends the section. New design: classified retries on the same model; then a **configurable emergency fallback** (decision below).

## 4. SendGrid

| Item | Finding |
|---|---|
| Input | `POST /v3/mail/send`, JSON personalizations / from / subject / content |
| Output | 202 Accepted (real send); 200 in sandbox mode |
| Errors | 400 payload, **401 bad key (clear JSON message, probe)**, 403 sender not verified, 413 too large, 429 rate, 5xx |
| Today | `tenacity` retries **any** exception 3x (wastes ~20 s on 401) |
| Fix | Retry only 429 / 5xx / network; fail fast on 4xx with CRITICAL log; save the HTML locally before sending so a failed send can be re-sent |

## 9. How errors are reported (new)

| Channel | What |
|---|---|
| `system_exceptions` table | Every error: run_id, component, model, error class, HTTP status, attempt, action taken |
| `logs/runs/<date>/run.json` | Per-run record (inputs, outputs, errors, tokens, cost) (logging step) |
| Email footer | One "system status" line: all OK / degraded sections / errors |
| Watchdog | Reads the above; alerts on non-retryable errors, missed runs, budget |

3. **Emergency fallback** after retries fail: (a) none, section shows "unavailable"; or (b) the other Pro-class model?
